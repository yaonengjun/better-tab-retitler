  任何以 * 开头并以 * 结尾的 key 都会被显示成 "Domain:"，这是 UI 文案误导。它实际上把三类东西都贴上了"Domain:"标签：
  - 真·域名规则（key 形如 *dongmonitor.jd.com*）
  - URL 通配规则（来自高级选项的 URL Pattern Matching）
  - 你这种把整段 URL 当 pattern 添加的情况

  你看到的内容是完整 URL 带 query，说明实际存储的 key 是：

  *https://dongmonitor.jd.com/ump/monitor/perfomance?endPointKey=...&frequency=oneMinute*

  这种 key 大概率是在"高级选项 → URL Pattern Matching"里手动加的（弹窗里的"Set for this domain"绝不会生成这种带路径和 query 的 key，看 background.js:357-362，它只会取 host 部分写成 *dongmonitor.jd.com*）。

  为什么 query 不同就匹配失败

  background.js:314-318 把 *...* 里面那一段当作正则表达式去测试 URL：

  const regexStr = pattern.substring(1, pattern.length - 1);
  const regex = new RegExp(regexStr);
  if (regex.test(url)) { ... }

  你的 pattern 内层字符串是：
  https://dongmonitor.jd.com/ump/monitor/perfomance?endPointKey=mobile_soa_search_rpc_wareCommonRpc_getWareDetail.search.first&frequency=oneMinute

  当成正则解释时：
  - ? 是量词，表示前一个字符可选。perfomance? 表示 perfomanc 或 perfomance，不表示字面量 ?。
  - . 是任意字符通配。
  - 因此到了 perfomance?endPointKey 这里，正则其实想匹配 perfomance 后面紧跟字面量 endPointKey（中间没有 ?）。而你的实际 URL 是 perfomance?endPointKey，中间有个 ?，正则匹配失败。

  理论上，这条规则在任何 URL 上都不应生效。如果第一条 URL 看起来生效过，可能是你当时是在 popup 里手动点了"设置标题"做了一次性应用，或者是 tab lock 在起作用，不是这条规则在工作。

  解决方案（任选一种）

  方案 A：直接用"Set for this domain"（推荐，最省事）

  在 popup 里访问 dongmonitor.jd.com 任何页面，选 "Set for this domain" 设置标题。会自动生成 *dongmonitor.jd.com*，所有该域名下的页面都生效。

  代价：整个 dongmonitor.jd.com 都会被改成同一个标题，无法区分页面。

  方案 B：用一个唯一子串作 URL Pattern（推荐用于多页面区分）

  去掉那些带 ? 的部分，挑一段在该页面 URL 中独一无二的子串包起来：

  *endPointKey=mobile_soa_search_rpc_wareCommonRpc_getWareDetail.search.first*

  - .test() 是非锚定匹配（background.js:318），只要 URL 里含有这个子串就命中，所以后面新加的 &start_time=...&end_time=... 不影响。
  - 子串里没有 ?，避免量词陷阱。
  - 里面的 . 仍然是正则通配，但只要字面量也是 .，依然能匹配上，无副作用。

  方案 C：保留原 pattern，但把元字符转义

  *dongmonitor\.jd\.com/ump/monitor/perfomance\?endPointKey=mobile_soa_search_rpc_wareCommonRpc_getWareDetail\.search\.first&frequency=oneMinute*

  把 ? 转义为 \?，. 转义为 \.。这样能精确匹配该路径 + 这两个 query 参数。然后由于 .test() 非锚定，URL 末尾追加 &start_time=...&end_time=... 不影响匹配，第二个 URL 也能命中。

  操作步骤

  1. 选项页找到那条 "Domain: https://dongmonitor.jd.com/..." 把它删除（别只编辑标题，key 没修）。
  2. 高级选项 → URL Pattern Matching，添加方案 B 或方案 C 的 pattern，标题填 搜索查询商卡的监控-首屏-UMP。
  3. 重新加载扩展（edge://extensions/ 点重载），刷新页面验证。

## 1.2 可能的方案讨论

```markdown
== prompt ==
 对于方案C，你看一下，是否可以通过修改代码来实现自动转义？ 先不要给改动，给我结论

```

⏺ 结论：可以，而且值得做。建议方向是把 URL Pattern 的语义从"裸正则"明确改为"glob 通配"——`*` 表示"任意字符序列"，其它一律按字面量处理（自动转义）。理由如下：

  **为什么可行**

  修改点很集中，只有两处：
  - `background.js:315-316` —— 把"内层字符串直接 new RegExp"改成"先 escape 再把 `*` 换成 `.*`，可选加 `^`/`$` 锚定"。
  - `options.js:288` 和 `options.js:345` —— 输入校验的正则 `/^\*.*\*$/`（保留或放宽均可，不影响功能）。

  转义函数标准做法：`str.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')`，再单独还原用户写的 `*`。

  **为什么应该做**

  1. 当前的语义和用户认知严重不符。功能名叫 "URL Pattern Matching"、输入示例是 `*example.com*`、文档示例是 `*github.com/*/issues/*`——所有这些都暗示 glob 通配，但代码里其实是裸正则。`?`、`.`、`(`、`)` 这些 URL 里高频出现的字符全是正则元字符，普通用户没法不踩坑。
  2. `*github.com/*/issues/*` 这个文档示例其实是错的。当成正则它表示"github.com + 0 个或多个 `/` + issues/"，根本匹配不到 `github.com/anthropics/issues/123`。说明开发者自己也是按 glob 心智模型设计的，代码实现走偏了。
  3. 改动风险可控。

  **必须权衡的代价**

  1. 向后兼容。已存在的旧规则如果当年是按"裸正则"写的（比如带 `\.`、`^`、`$`、`[a-z]+` 这种），改完语义后行为会变。三种处理选择：

    - 一次性迁移脚本：扩展启动时扫描 `chrome.storage.sync`，把旧 pattern 重写。
    - 加版本字段共存：新规则带 `{ title, mode: 'glob' }`，老规则按旧逻辑跑。
    - 直接断代：在 release notes 标注 breaking change，让用户重建少量规则。
    
    对一个个人/小众扩展，第三种最简单且风险低（存量规则估计也极少）。
  2. 失去裸正则的表达力。极少数高级用户可能依赖 `^`、`$`、字符类等特性。可以加一个 "Regex Mode" 复选框作为逃生舱，但 99% 的场景下 glob 已经够用。
  3. `*` 必须作为保留字符。如果某个 URL 里本身含 `*`（极罕见），glob 模式下无法表达字面 `*`。可约定 `\*` 转义。

  **推荐结论**

  值得做，推荐选 glob 方案 + 直接断代。同时把"严格前缀匹配"的需求自然吸收进去——glob 模式下 `*` 锚定的语义变成：
  - `prefix*` = 前缀匹配
  - `*substring*` = 子串匹配
  - `prefix*suffix` = 前缀 + 后缀
  - `exacturl` = 完全相等（其实没必要，已经有 exact match 通道了）

  如果决定做，请告知，我再给具体改动方案。

## 1.3 方案核实与补充（2026-05-18）

对上述方案与实际代码（background.js、options.js）逐行比对后，原方案整体准确，补充两处修正：

### 修正 1：`options.js` 的 `formatKey` 展示函数无需修改

原方案将输入校验层（`options.js:286-296, 345-349`）与展示层混在一起描述，导致容易误解为需要修改 `formatKey`。实际上：

- **`formatKey`（L208-L209）** 仅负责 UI 展示，将所有 `*...*` 格式的 key 显示为 `Domain: xxx`。改为 glob 后，存储的 key 格式不变，`formatKey` **无需修改**，功能不受影响。
- 若想更友好，可将标签从 `Domain:` 改为 `Pattern:`，但这是纯 UI 优化，不影响功能正确性，可选做。
- **真正需要改的只有两处**：
  1. `background.js:315-316`——匹配逻辑从裸正则改为 glob 转义
  2. `options.js:288` 和 `options.js:345`——输入校验的正则（保留或放宽均可）

### 修正 2：域名规则与 URL Pattern 共用 `*...*` 格式，需防止 glob 误处理

原方案未提及这一隐患。`checkAndUpdateTitle` 中有两条独立分支：

```js
// 分支 A：域名匹配（L300-L308）——构造 *host* 后精确查 rules key
const domain = `*${domainMatch[1]}*`;
if (rules[domain]) { ... }

// 分支 B：URL Pattern 遍历（L311-L329）——遍历所有 startsWith('*') 的 key
for (const pattern in rules) {
  if (pattern.startsWith('*') && !pattern.startsWith('*Tab#') && pattern !== 'options') {
    const regex = new RegExp(regexStr);
    if (regex.test(url)) { ... }
  }
}
```

两个分支互斥（分支 A 命中就不走分支 B），但存在隐患：用户若通过高级选项手动添加了 `*dongmonitor.jd.com*` 这类**纯域名格式的 pattern**，改为 glob 后，分支 B 会对该 key 做 glob 解析，语义上与分支 A 一致，本身无害，但可能产生非预期的重复逻辑。

**推荐处理方式（改动时须考虑）**：在分支 B 的遍历中，过滤掉"内容不含 `/` 和 `?` 的纯域名格式 key"，将此类 key 完全留给分支 A 处理：

```js
const inner = pattern.slice(1, -1);
// 不含路径或 query 的 key 视为域名规则，跳过 URL Pattern 处理
if (!inner.includes('/') && !inner.includes('?')) continue;
```

# 二、最终改动方案

## 2.1 方案概述

采用 **glob 方案 + 直接断代**：将 URL Pattern 的匹配语义从"裸正则"改为"glob 通配"。  
用户输入的 pattern 中，`*` 是唯一的通配符，表示"任意字符序列（含空）"；其余所有字符（包括 URL 中高频出现的 `?` `.` `(` `)` `&` `=`）均自动作为字面量处理，**无需手动添加转义斜杠**。

### 支持的匹配模式

| 写法 | 语义 | 示例 |
|------|------|------|
| `prefix*` | 前缀匹配：URL 以 prefix 开头，后面任意 | `https://dongmonitor.jd.com/ump*` |
| `*substring*` | 子串匹配：URL 中包含 substring | `*endPointKey=mobile_soa*` |
| `prefix*suffix` | 前缀 + 后缀：URL 以 prefix 开头且以 suffix 结尾 | `https://example.com/*/detail` |

> **注意**：不再支持 `exacturl`（无 `*`）写法，精确 URL 请使用已有的 exact match 规则通道。

## 2.2 改动文件与改动点

### 文件 1：`js/background.js`

**改动位置：`checkAndUpdateTitle` 函数，L311-L329（URL Pattern 遍历分支）**

核心：把「直接 `new RegExp(regexStr)`」替换为「glob → 正则的转换函数」。

#### 新增工具函数（放在文件顶部常量区附近）

```js
/**
 * 将用户输入的 glob pattern（内层，即去掉首尾 * 之后的部分或完整 pattern）
 * 转换为等价的 RegExp 对象。
 * 规则：
 *   - 除 * 以外的所有字符一律转义为正则字面量
 *   - * 转换为 .* （匹配任意字符序列，含空串）
 *   - 整体用 ^ 和 $ 锚定，保证是完整 URL 匹配而非子串匹配
 *
 * 示例：
 *   globToRegex('*foo.bar*')  => /^.*foo\.bar.*$/
 *   globToRegex('https://example.com*')  => /^https://example\.com.*$/
 *   globToRegex('*search*detail*') => /^.*search.*detail.*$/
 */
function globToRegex(pattern) {
  // 转义正则元字符（除 * 外全部转义）
  const escaped = pattern.replace(/[.+?^${}()|[\]\\]/g, '\\$&');
  // 把转义后的 \* 还原（上一步不动 *，这里把 * 换成 .*）
  const regexStr = escaped.replace(/\*/g, '.*');
  return new RegExp('^' + regexStr + '$');
}
```

> **为什么用 `^...$` 全锚定？**  
> glob 的 `prefix*` 语义就是"以 prefix 开头，后面任意"，全锚定后 `^prefix.*$` 精确表达了这个语义。  
> 旧版用 `.test(url)` 不锚定，会在 URL 任意位置找匹配，行为反直觉。

#### 修改 URL Pattern 遍历分支

```js
// 改动前（L311-L329）
if (!ruleMatched) {
  for (const pattern in rules) {
    if (pattern.startsWith('*') && !pattern.startsWith('*Tab#') && pattern !== 'options') {
      try {
        const regexStr = pattern.substring(1, pattern.length - 1);  // ← 删除
        const regex = new RegExp(regexStr);                          // ← 替换
        if (regex.test(url)) {
          ...
        }
      } catch (e) { ... }
    }
  }
}

// 改动后
if (!ruleMatched) {
  for (const pattern in rules) {
    if (pattern.startsWith('*') && !pattern.startsWith('*Tab#') && pattern !== 'options') {
      // 过滤纯域名格式 key（不含 / 和 ?），留给域名匹配分支处理，避免重复
      const inner = pattern.slice(1, -1);
      if (!inner.includes('/') && !inner.includes('?') && !inner.includes('*')) continue;

      try {
        const regex = globToRegex(pattern);   // ← 直接传完整 pattern
        if (regex.test(url)) {
          const newTitle = rules[pattern].title;
          newTitleToSet = processUrlPatternReplacement(newTitle, currentTitle, url, regex);
          ruleMatched = true;
          break;
        }
      } catch (e) {
        console.error("URL pattern matching error:", e);
      }
    }
  }
}
```

> **关键变化对比：**
> - 旧：`pattern.substring(1, pattern.length - 1)` 去掉首尾 `*` 后当裸正则用  
> - 新：`globToRegex(pattern)` 对完整 pattern 做字面量转义，`*` 转 `.*`，全锚定

| `https://dongmonitor.jd.com/...?endPointKey=...search.first&frequency=oneMinute` | ✅ 命中 |
| `https://dongmonitor.jd.com/...?frequency=oneMinute&endPointKey=...search.first` | ✅ 命中（参数顺序无关） |
| `https://other.com/...?endPointKey=...search.first` | ✅ 命中（跨域也匹配，如不想要则用前缀匹配） |

### 场景 C：前缀 + 后缀匹配

用户输入 pattern：  
```
https://dongmonitor.jd.com/ump/monitor/perfomance*frequency=oneMinute
```

| 测试 URL | 结果 |
|----------|------|
| `...perfomance?endPointKey=xxx&frequency=oneMinute` | ✅ 命中 |
| `...perfomance?endPointKey=xxx&frequency=oneMinute&start_time=xxx` | ❌ 不命中（末尾多了参数） |

## 2.5 断代说明

本次改动直接断代，不做旧规则迁移。影响范围：

- 旧 URL Pattern 规则若是**纯字面量 URL 片段**（无 `\.`、`^`、`$` 等正则语法），改后行为**不变**（原来能匹配的现在仍能匹配，因字面量转义后语义等价）。
- 旧规则若依赖**正则特殊语法**（如 `[a-z]+`、`\d`），改后将失效，需用户手动重建。对于个人扩展，此类规则极少。
- **域名规则**（通过 popup 的"Set for this domain"创建的 `*host*`）完全不受影响，走独立的域名匹配分支。

## 2.6 用法速查：四种匹配模式示例

以实际的 `dongmonitor.jd.com` URL 为例：

**实际 URL：**
```
https://dongmonitor.jd.com/ump/monitor/perfomance?endPointKey=mobile_soa_search_rpc_wareCommonRpc_getWareDetail.search.first&frequency=oneMinute&start_time=xxx&end_time=xxx
```

---

### 前缀匹配 — `prefix*`

匹配以某段开头、后面随便跟什么：

```
https://dongmonitor.jd.com/ump/monitor/perfomance?endPointKey=mobile_soa_search_rpc_wareCommonRpc_getWareDetail.search.first*
```

| 测试 URL | 结果 |
|----------|------|
| `...search.first&frequency=oneMinute` | ✅ 命中 |
| `...search.first&frequency=fiveMinute&start_time=xxx` | ✅ 命中 |
| `...other_endpoint&frequency=oneMinute` | ❌ 不命中（endPointKey 不同） |

---

### 关键词匹配 — `*keyword*`

URL 里只要包含这段就命中，参数顺序无所谓：

```
*endPointKey=mobile_soa_search_rpc_wareCommonRpc_getWareDetail.search.first*
```

| 测试 URL | 结果 |
|----------|------|
| `https://dongmonitor.jd.com/...?endPointKey=...search.first&frequency=oneMinute` | ✅ 命中 |
| `https://dongmonitor.jd.com/...?frequency=oneMinute&endPointKey=...search.first` | ✅ 命中（参数顺序换了也能中） |
| `https://other.com/...?endPointKey=...search.first` | ✅ 命中（跨域也中；只想匹配特定域请用前缀匹配） |

---

### 后缀匹配 — `*suffix`

URL 必须以某段结尾，前面随便：

```
*frequency=oneMinute
```

| 测试 URL | 结果 |
|----------|------|
| `https://dongmonitor.jd.com/...?endPointKey=xxx&frequency=oneMinute` | ✅ 命中 |
| `...frequency=oneMinute&start_time=xxx` | ❌ 不命中（末尾还有其他参数） |
| `...frequency=fiveMinute` | ❌ 不命中（frequency 值不同） |

---

### 前缀 + 后缀组合 — `prefix*suffix`

锁定开头和结尾，中间任意：

```
https://dongmonitor.jd.com/ump*frequency=oneMinute
```

| 测试 URL | 结果 |
|----------|------|
| `https://dongmonitor.jd.com/ump/monitor/perfomance?endPointKey=xxx&frequency=oneMinute` | ✅ 命中 |
| `https://other.com/ump/...?frequency=oneMinute` | ❌ 不命中（域名不对） |
| `https://dongmonitor.jd.com/ump/...?frequency=oneMinute&start_time=xxx` | ❌ 不命中（末尾多了参数） |

---

> **核心规则：** `*` 是唯一通配符，`.` `?` `&` `=` 等字符无需手动转义，直接写原始 URL 片段即可。
