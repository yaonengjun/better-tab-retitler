# 增加新的匹配规则需求 (Keyword match & Prefix match)

## 一、需求梳理

根据需求，我们需要在扩展的 Popup 界面增加两种持久化规则，并重新定义规则的显示顺序与优先级：

### 1. 新增规则定义
- **Keyword match**：关键字匹配。当 URL 中包含用户指定的关键字时（如 `prepub-zyy`），展示设定的标题。
- **Prefix match**：前缀匹配。当 URL 以用户指定的前缀开头时（如 `http://jagile.jd.com/jdosCD/ls/instance/mobile-search-soa`），展示设定的标题。
- 这两项均属于**持久化规则**，基于 `chrome.storage.sync` 进行跨端账号同步。

### 2. 界面展示顺序与文案
弹出菜单（Popup）中的单选项顺序及文案要求严格按以下顺序排列：
1. Only for this time (非持久化)
2. Set for this tab (仅当前标签页)
3. Keyword match [P1]
4. Prefix match [P2]
5. Only exact match [P3]
6. Set for this Domain [P4]

### 3. 匹配优先级机制
- 优先级的业务定义：数字越大，优先级越高，即 **P4 > P3 > P2 > P1**。
- 结合需求，当一个页面的 URL 同时命中多种规则时，生效顺序应为：
  **Set for this Domain [P4] > Only exact match [P3] > Prefix match [P2] > Keyword match [P1]**。
  *(注：临时性规则 `Set for this tab` 和 `Only for this time` 作为用户当前会话的强行干预，优先级天然高于所有持久化规则)*。

## 二、改动方案设计

为了实现上述需求，计划对以下模块进行改造：

### 1. UI 交互层改造 (`popup.html` & `popup.js` & `css/popup.css`)
- **新增选项**：在 `popup.html` 的 radio button 列表中插入对应的选项，调整顺序。
- **动态输入框 (关键交互)**：
  因为 Domain 和 Exact match 可以由程序自动从当前 URL 提取（自动获取域名或全路径），但 **Keyword** 和 **Prefix** 必须由用户指定具体的范围。
  - **方案**：当用户在 Popup 中点击选中 `Keyword match [P1]` 或 `Prefix match [P2]` 时，下方动态展开一个额外的文本输入框（Pattern Input）。
  - **智能填充**：
    - 若选 Prefix：默认将当前页面的完整 URL 填充进去，用户可从尾部删减，留下所需的前缀部分。
    - 若选 Keyword：默认留空（或给一个提示），让用户输入特定的关键字（如 `prepub-zyy`）。
- **多语言适配**：更新 `_locales/` 下的 `messages.json`，增加新选项的翻译字段。

### 2. 数据存储层改造
根据之前已经引入的 Glob 通配符支持（`doc/20260518-100-前缀匹配问题.md`），底层的存储非常容易映射：
- **Keyword match**：用户输入 `prepub-zyy`，代码存储的 key 为 `*prepub-zyy*`。
- **Prefix match**：用户输入 `http://.../mobile-search-soa`，代码存储的 key 为 `http://.../mobile-search-soa*`。
- 这两种格式天生兼容现有的基于账号的 `chrome.storage.sync`。

### 3. 核心匹配逻辑改造 (`js/background.js`)
目前 `checkAndUpdateTitle` 函数的优先级逻辑是串行判断的，需要根据 P4 到 P1 的顺序彻底重构：
- **第 0 优先级**：检测 `Tab#${tabId}` 标签锁。
- **第 1 优先级 (P4)**：检测 Domain 匹配（拼接 `*host*` 去 rules 匹配）。
- **第 2 优先级 (P3)**：检测 Exact URL 匹配。
- **第 3 优先级 (P2)**：遍历所有的 Glob 规则（含有 `*`），过滤出**以 `*` 结尾但不以 `*` 开头**的规则（即 Prefix 规则），转成正则后尝试匹配当前 URL。若有多个 Prefix 命中，优先选择长度最长的前缀（最精确匹配）。
- **第 4 优先级 (P1)**：遍历所有的 Glob 规则，过滤出**以 `*` 开头且以 `*` 结尾**的规则（即 Keyword 规则），转成正则后尝试匹配。

### 4. 选项设置页改造 (`options.html` & `options.js`)
- **默认策略设置**："Default Options" 面板中的下拉框需要增加这两个新策略。
- **规则列表显示**：在 "Saved Titles" 中，将新规则展示出来。

## 三、待确认的开放性问题 (Open Questions)

在开始写代码前，有两个业务逻辑层面的问题需要向您确认：

> [!WARNING]
> **1. 优先级的反转确认 (Domain vs Exact)**
> 按照您设定的 P4 到 P1，**Domain [P4] 的优先级高于 Exact match [P3]**。
> 这意味着：如果您为整个域名 `jd.com` 设置了标题为 "京东主站"，然后又为 `jd.com/item/123` 设置了精确标题 "商品详情"，当您访问商品详情页时，由于 P4 > P3，插件将应用 "京东主站" 这个标题。
> 通常的逻辑是越精确的规则优先级越高（精确 > 前缀 > 域名）。**请问您确定要让 Domain 的优先级大于 Exact match 吗？**

> [!NOTE]
> **2. 动态输入框交互**
> 像上文提到的，Keyword 和 Prefix 需要用户提供具体的词。我计划在用户选中这两项时，于弹窗内动态显示一个输入框让用户手填/删改。请确认这种交互设计是否符合您的预期？
