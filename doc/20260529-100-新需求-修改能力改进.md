# 新需求：修改能力改进 (编辑标题、URL和模式)

## 需求说明
在 Options 页面（已保存的规则列表）中，原本点击“✏️ 编辑”按钮只能通过 `prompt` 弹窗修改规则的 **标题 (Title)**。
现在的需求是：**不仅能够修改标题，还要能够修改该规则对应的 URL 或匹配模式 (Pattern)**。

## 结论与可行性
**完全可以实现，并且对现有架构没有破坏性。**

### 可行性分析
在 `chrome.storage.sync` 中，规则的存储结构是 `键值对 (Key-Value)`，其中：
- **Key (键)**: 存储的是 URL 或者是匹配模式（如 `*jagile.jd.com*` 等）。
- **Value (值)**: 存储的是 `{ title: "...", id: "..." }` 对象。

因此，修改匹配模式本质上是**修改存储中的 Key**。在 Chrome Storage 中，我们无法直接“重命名”一个 Key，但可以通过**“新增一个具有新 Key 的数据，同时删除旧 Key 的数据”**这一组合操作来完美实现。由于该规则的内部 `id` 不会改变，这在业务逻辑上仍然被视为对同一条规则的修改。

## 大致改动范围与方案

### 1. 交互体验 (UI / UX) 升级
考虑到如果要连续弹出两次 `prompt`（一次问模式，一次问标题）体验非常糟糕，而且极容易出错，我们建议**放弃原有的 `prompt` 弹窗**，改用以下两种方案之一：

- **方案 A (推荐)：Inline Edit (内联编辑)**
  点击“✏️ 编辑”按钮后，将该规则展示区的“匹配模式”和“标题”直接转换成可编辑的 `<input>` 输入框。同时，原本的编辑按钮变成绿色的“💾 保存”按钮，并出现一个“取消”按钮。用户在原地修改完成后点击保存。
  
- **方案 B：Modal Dialog (自定义弹窗)**
  在 `options.html` 中新增一个隐藏的模态框 (Modal)。点击编辑时弹出该模态框，里面包含“匹配模式”和“目标标题”两个输入框。

### 2. 代码逻辑调整 (`options.js`)
无论采用上述哪种 UI 方案，核心的数据更新逻辑是相同的：
1. **获取新旧数据**：获取用户修改后的 `newKey` (新匹配模式) 和 `newTitle` (新标题)，以及原本的 `oldKey`。
2. **校验逻辑**：检查 `newKey` 是否为空。如果是前缀/关键字匹配，还可以顺带检查格式是否包含 `*`。
3. **Storage 更新**：
   ```javascript
   // 如果匹配模式没有改变，只是改了标题
   if (newKey === oldKey) {
       const update = {};
       update[oldKey] = { title: newTitle, id: value.id };
       chrome.storage.sync.set(update, () => loadSavedTitles());
   } 
   // 如果匹配模式发生了改变
   else {
       const update = {};
       update[newKey] = { title: newTitle, id: value.id }; // 写入新 Key
       
       chrome.storage.sync.remove(oldKey, () => { // 删除旧 Key
           chrome.storage.sync.set(update, () => {
               loadSavedTitles();
           });
       });
   }
   ```

### 3. DOM 结构与样式的微调 (`options.html` / `css/options.css`)
如果采用**方案 A (内联编辑)**：
- 在 `options.js` 动态渲染列表时，为每条规则构建“阅读模式”和“编辑模式”两套 DOM 元素，通过点击编辑按钮进行展示/隐藏的切换。
- 在 `css/options.css` 中增加输入框的样式，使其融入当前的列表卡片设计。

### 总结
该需求技术上完全可行。改动范围主要集中在 `options.js`（增加编辑状态切换和更新旧 Key 的逻辑）以及 `options.css`（增加处于编辑状态时的输入框样式）。不会涉及核心的匹配机制（`background.js`），因此风险极低。
